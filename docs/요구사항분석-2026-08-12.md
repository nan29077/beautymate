#### 관련 라우트

| 경로 | 파일 | 역할 | 로그인 관련 |
|---|---|---|---|
| `/shop/[slug]` | `src/app/(public)/shop/[slug]/page.tsx` | 점집 공개 페이지 (프로필 → 오늘의 예약 현황 → 상담 메뉴 → 소개 → 예약 달력 → 콘텐츠) | **로그인/회원가입 진입점 없음** |

| `/auth/register` | `src/app/auth/register/page.tsx` | 전역 회원가입 | URL `?ref=<slug>` 가 있을 때만 점집명 배너 표시 |
| `/api/auth/[...nextauth]` | NextAuth v5 핸들러 | JWT 세션, credentials + Kakao/Naver/Google | 단일 테넌트 |
| `/api/auth/register` | 자체 가입 API | `body.sellerRef` 만 신뢰해 귀속 처리 | 쿠키 fallback **의도적으로 제거됨** |

#### 이미 존재하는 "상담사 귀속" 인프라

```
[유입] /shop/[slug] 또는 /products/[id]?ref=slug 또는 /auth/register?ref=slug
   │
   ├─ src/middleware.ts
   │     └─ sb_ref 쿠키 저장 (httpOnly, 7일, last-click)
   │
   ├─ ShopContextSync.tsx (점집 메인에서만)
   │     └─ sb_shop 쿠키 저장 (JS, 30일) = { slug, name, logo }
   │        → 서브페이지(/cart, /my/*, /products/*)에서 점집 헤더·하단바 유지
   │        → /auth/login 이 이 쿠키를 읽어 로그인 후 점집으로 복귀
   │
[가입] linkReferralForNewBuyer()  (src/lib/referral.ts)
   ├─ 우선순위: referralCode → sellerRef(slug)
   ├─ 미승인 상담사는 매핑 안 함
   ├─ BuyerProfile.upsert → primarySellerId / referredBySellerId / referralCode
   └─ SellerProfile.totalFans++
```

**호출 경로 2개:**
- 일반 가입 → `src/app/api/auth/register/route.ts` (body 의 `sellerRef` **만** 신뢰)
- 소셜 가입 → `src/lib/auth.ts` `events.createUser` (**`sb_ref` 쿠키를 읽음**)

> ⚠️ **정책 불일치 발견**: 소셜 가입은 쿠키 fallback 을 쓰고 일반 가입은 쓰지 않는다. `auth/register/page.tsx` 주석에 "점집 방문 후 남은 쿠키 때문에 일반 가입도 상담사 초대로 표시되는 문제가 있어 제거함" 이라고 기록됨. 즉 **같은 유입 경로인데 가입 수단에 따라 귀속 여부가 달라진다.**

#### 현재 상태 요약

| 구성요소 | 상태 |
|---|---|
| 점집 컨텍스트 유지(쿠키) | ✅ 있음 (`sb_ref`, `sb_shop`) |
| 로그인 후 점집 복귀 | ✅ 있음 (`getShopAwareLoginPath`) |
| 가입 시 상담사 귀속 | ⚠️ 부분 — 소셜은 쿠키, 일반은 URL `?ref=` 필수 |
| 상담사별 고객 목록 | ✅ 있음 (`/seller/customers`, `/seller/fans`) |
| **점집 페이지 안의 로그인/가입 UI** | ❌ **없음** |
| **점집 브랜딩 로그인 화면** | ❌ 없음 (전역 사주메이트 UI) |
| 점집별 계정 분리 | ❌ 없음 (전역 `User.email @unique`) |

### A-2. "상담사 귀속 로그인"이란 정확히 무엇인가

사용자 설명("셀러브릭스의 셀러 샵 로그인 방식과 동일")을 코드로 되짚어보면, **셀러브릭스의 셀러샵 로그인은 실제로 아래 방식이었다**:

> 계정 자체는 전역(NextAuth 단일 User 테이블)이고, **가입 시점의 유입 셀러를 `BuyerProfile.primarySellerId` 에 귀속**시켜 그 셀러의 "내 팬"으로 관리하는 방식.

즉 **완전히 분리된 인증 시스템이 아니라 "귀속이 붙는 전역 로그인"** 이다. 그리고 그 뼈대는 **이미 이 코드베이스에 다 들어 있다**. 실제로 없는 것은 다음 4가지다.

1. 점집 페이지 안에 **로그인/회원가입 진입점 UI** 가 없다
2. 로그인·가입 화면에 **점집 브랜딩**(상담사 이름/로고/테마색)이 없다
3. 일반 가입 시 **쿠키 fallback 이 없어 귀속이 유실**된다 (점집 → 로그인 → "회원가입" 링크 클릭 시 `?ref=` 가 사라짐)
4. `primarySellerId` 는 **최초 1회 성격**이라, 이미 가입한 고객이 다른 점집을 방문했을 때의 정책이 없다

따라서 해석은 세 층위로 나뉜다.

| 해석 | 의미 | 계정 |
|---|---|---|
| **(가) 귀속형** | 전역 계정 + 가입 시 상담사 귀속 (셀러브릭스 원형) | 1개 (이메일 전역 유일) |
| **(나) 멤버십형** | 전역 계정 + **점집별 멤버십 N:N** — 한 사람이 여러 점집의 회원이 될 수 있음 | 1개 |
| **(다) 테넌트형** | 점집마다 완전히 분리된 계정 — 같은 이메일로 점집 A/B 각각 가입 | 점집 수만큼 |

---

### A-3. 현재 NextAuth 구조에서의 구현 가능성

**전제 확인:**
- NextAuth v5, `session: { strategy: "jwt" }` — 세션이 서버 테이블이 아니라 JWT 이므로 **토큰에 필드를 추가하는 방식이 가장 저렴**하다 (`jwt`/`session` 콜백 이미 커스터마이즈되어 있음: `role`, `sellerSlug`, `mustResetPassword`)
- `PrismaAdapter` 사용 + `User.email @unique` — **(다) 테넌트형은 이 제약을 깨야 한다**
- Credentials provider 의 `authorize()` 는 자유롭게 확장 가능 — 추가 credential(예: `shopSlug`)을 받아 검증할 수 있다
- `events.createUser` 는 **OAuth 신규 가입에서만** 호출된다 (credentials 가입은 register API 가 직접 처리)

#### 옵션 2 — 멤버십형 (점집별 N:N 회원) ⭐ 권장 (2단계)

**개념**: 옵션 1 위에 `ShopMembership` 모델을 얹어, 한 계정이 여러 점집의 회원이 될 수 있게 한다. 로그인은 전역, "이 점집의 회원인가"는 멤버십으로 판정.

**스키마 추가**

```prisma
model ShopMembership {
  id           String   @id @default(cuid())
  userId       String
  user         User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  sellerId     String
  seller       SellerProfile @relation(fields: [sellerId], references: [id], onDelete: Cascade)
  joinedVia    String   // "SHOP_PAGE" | "SHORT_LINK" | "REFERRAL_CODE" | "RESERVATION"
  isPrimary    Boolean  @default(false)   // BuyerProfile.primarySellerId 와 동기화
  nickname     String?                    // 점집 안에서만 쓰는 별칭 (선택)
  createdAt    DateTime @default(now())

  @@unique([userId, sellerId])
  @@index([sellerId])
  @@map("shop_memberships")
}
```

**동작**
- 점집 로그인/가입 시 해당 점집 멤버십을 `upsert` (없으면 생성)
- 첫 멤버십은 `isPrimary: true` + `BuyerProfile.primarySellerId` 동기화 (기존 정산·추천 로직 무손상)
- `/shop/[slug]` 진입 시 "가입한 점집" / "처음 방문한 점집" 을 구분해 CTA 분기
- `/seller/customers` 를 멤버십 기준으로 조회하면 상담사별 고객 목록이 정확해진다

**장점**: 셀러브릭스식 UX 를 유지하면서 다중 점집 이용을 자연스럽게 지원. `User.email @unique` 유지. 정산/추천 로직 무변경.
**단점**: 스키마 마이그레이션 필요 (**⚠️ 운영 DB 직결 — `prisma migrate diff` 선행 필수, `db push --accept-data-loss` 절대 금지**). 기존 `BuyerProfile` 데이터 백필 스크립트 필요. **3~5일 공수.**

#### 옵션 3 — 테넌트형 (점집별 완전 분리 계정) ❌ 비권장

**개념**: 같은 이메일로 점집 A/B 에 각각 별도 계정을 만든다.

**필요 변경**
- `User.email @unique` → `@@unique([email, tenantSellerId])` 로 변경 (**전 테이블 파급**)
- `PrismaAdapter` 가 이메일 기준으로 동작하므로 **어댑터 커스터마이징 또는 자체 구현** 필요
- OAuth(Kakao/Naver/Google)는 provider 계정 1개 → 테넌트 N개 매핑이 되지 않아 **소셜 로그인이 사실상 붕괴**
- 비밀번호 찾기·아이디 찾기·관리자 회원 관리·정산 등 **모든 사용자 조회 경로 재작성**

**결론**: 사용자가 말한 "셀러브릭스 셀러샵 로그인"은 이 방식이 **아니었다**(전역 계정 + 귀속). 소셜 로그인 3종을 이미 운영 중인 상황에서 이 방향은 비용 대비 이득이 없다. **권장하지 않음.**

### A-5. 권장안

**1단계(즉시, 1~2일): 옵션 1** — 점집 안에서 로그인·가입이 완결되도록 UI/라우트를 만들고, 귀속 유실 경로(일반 가입 쿠키 fallback)를 막는다. 스키마 변경이 없어 운영 DB 리스크가 0이다.

**2단계(예약 플로우 안정화 이후, 3~5일): 옵션 2** — `ShopMembership` 도입으로 다중 점집 이용과 상담사별 고객 관리를 정확하게 만든다.

**의사결정이 필요한 지점 2가지**
1. 이미 가입한 고객이 **다른 점집**을 방문해 예약하면 귀속을 옮길 것인가, 추가할 것인가? (옵션 2 는 "추가", 옵션 1 은 "최초 고정")
2. 점집 로그인 화면에서 **소셜 로그인**을 허용할 것인가? 허용 시 `events.createUser` 가 `sb_ref` 를 읽는 현재 로직으로 커버되지만, 점집 세그먼트를 확실히 하려면 OAuth `state` 에 slug 를 실어 보내는 편이 안전하다.

## 요구사항 B — 예약 → 결제 → 확정 플로우

### B-1. Reservation 모델 상태값 (schema.prisma)

```prisma
enum ReservationStatus {
  PENDING    // 예약 신청 (결제/확정 대기)   ← 스키마 주석이 이미 요구사항과 일치
  CONFIRMED  // 상담사 확정
  COMPLETED  // 상담 완료
  CANCELLED  // 취소
  NO_SHOW    // 노쇼
}

enum PaymentStatus {
  PENDING
  COMPLETED
  FAILED
  REFUNDED
}
```

`Reservation` 모델의 결제 관련 필드는 **이미 완비**되어 있다.

| 필드 | 용도 |
|---|---|
| `status` / `paymentStatus` | 예약 상태 / 결제 상태 (2축 분리 — 요구사항에 정확히 부합) |
| `paymentMethod`, `pgProvider`, `pgTid`, `pgAuthData` | PG 승인 정보 |
| `paidAt`, `confirmedAt`, `completedAt`, `noShowAt`, `cancelledAt`, `refundedAt` | 상태 전이 시각 |
| `cancelRequestedAt` ~ `cancelFromSettlement` | 상담사 취소요청 → 관리자 승인 워크플로 |
| `sellerFeeRateSnap` | 정산 요율 스냅샷 |
| `timeSlot` (역참조) | `TimeSlot.reservationId @unique` 로 1:1 슬롯 점유 |

> 즉 **모델은 요구사항을 이미 충족한다. 문제는 전적으로 흐름(호출 그래프)에 있다.**

### B-2. 결제 연동 구현 수준

**PG 3사 서버 구현은 실재하며, 완성도가 높다.**

| PG | 라우트 | 상태 |
|---|---|---|
| 스마트로 (`smartropay`) | `prepare`, `result` | ✅ 해시 검증, 금액 이중 검증(요청/승인), 승인 API 호출, `PaymentLog` 적재 |
| 온기 (`ongi`) | `prepare`, `callback` | ⚠️ 동작하나 **서명/IP 검증 없음** (P0-8) |
| SeedPay | `prepare`, `launch`, `result`, `cancel` | ✅ 해시 검증 + 취소(부분/전체) 지원 |

**결제 완료 → 예약 확정 로직은 존재한다.** 예: `src/app/api/payments/smartropay/result/route.ts:158`

```ts
await prisma.reservation.update({
  where: { id: order.id },
  data: {
    status: "CONFIRMED",          // ← 결제 완료 시 예약 확정
    paymentStatus: "COMPLETED",
    paymentMethod: approval.PayMethod || "EASYPAY",
    pgProvider: "smartropay",
    pgTid: approval.Tid ?? Tid,
    pgAuthData: JSON.stringify(approval),
    paidAt: new Date(),
  },
});
await notifyOrderPlacedToSeller(order.id).catch(...);   // 상담사에게 예약접수 알림톡
```

SeedPay(`result/route.ts:155`), 온기(`callback/route.ts:145`)도 동일 패턴. **요구사항 B("결제 완료 후 예약 확정")의 서버 구현은 이미 존재한다.**

### B-3. 결제 미연결 구간 — 정확히 어디부터 어디까지인가

현재 예약 생성 경로가 **2개**이고, 둘 다 결제까지 도달하지 못한다.

#### 경로 ① 체크아웃 경로 — `/checkout` → `/api/orders` POST

```
CheckoutClient.tsx (L381)
  POST /api/orders
    body: { sellerId, campaignId, items, customerName, customerPhone,
            shippingMemo, snsAccounts, couponCode }
                          ▲
                          └── reservationDate / reservationTime 없음 (입력 UI 자체가 없음)

/api/orders/route.ts (L96~104)
  if (!reservationDateValue || NaN) → 400 "예약 날짜가 올바르지 않습니다."
  if (!/^\d{2}:\d{2}$/.test(reservationTime)) → 400 "예약 시간이 올바르지 않습니다."
```

> 🔴 **단절 지점 1**: `/api/orders` POST 가 **항상 400**. 그 뒤의 `smartropay/prepare` → `result` → `CONFIRMED` 는 **완성되어 있으나 도달 불가.**
> 추가로 이 경로는 `TimeSlot` 을 점유하지 않고 `maxDailySlots` 카운트만 본다 → 도달 가능해지더라도 **이중예약이 발생한다.**

#### 경로 ② 예약 플로우 경로 — `/shop/[slug]/book` → `/api/reservations` POST

```
BookingFlow.tsx (L127) handleSubmit()
  POST /api/reservations  { sellerId, productId, timeSlotId, reservationDate,
                            reservationTime, customerName, ... }
        │
        ▼
/api/reservations/route.ts (L149~187)
  reservation.create({ status: "PENDING", paymentStatus: "PENDING", ... })
  timeSlot.update({ isAvailable: false, reservationId })   ← 슬롯 점유는 정상
        │
        ▼  201 응답
BookingFlow.tsx (L145~148)
  setDoneReservationId(...) ; setStep("done")
  화면: "예약이 신청되었습니다! 상담사 확인 후 예약이 확정됩니다."
        │
        ▼
      ❌ 끝. 결제로 넘어가는 코드가 존재하지 않음.
```

> 🔴 **단절 지점 2**: `/api/reservations` POST 201 응답 **직후부터 `/api/payments/*/prepare` 호출 사이**가 통째로 비어 있다.
> 🔴 **문구 불일치**: BookingFlow 의 안내가 "상담사 확인 시 최종 확정"(L457) — 요구사항("결제 완료 후 확정")과 반대다.
> 🔴 **알림 미연결**: `/api/reservations` 는 `notifyOrderPlacedToSeller` 를 호출하지 않는다. `notifyReservationConfirmedToCustomer`(`src/lib/alimtalkTriggers.ts:42`)는 **정의만 있고 호출부 0곳**.

#### 단절 구간 요약도

```
[경로 ①]  Cart/Checkout ──400──╳                                    (결제 도달 불가)
                               ┊
[경로 ②]  BookingFlow ──201──> Reservation(PENDING/PENDING)
                                        ┊
                                        ╳  ← ★ 미구현 구간
                                        ┊
                               /api/payments/{smartro|ongi|seedpay}/prepare   ✅ 구현됨
                                        ↓
                               PG 결제창 (사용자 승인)                          ✅
                                        ↓
                               /api/payments/*/result|callback                 ✅ 구현됨
                                        ↓
                               status=CONFIRMED, paymentStatus=COMPLETED       ✅ 구현됨
                               notifyOrderPlacedToSeller()                     ✅ 구현됨
                                        ↓
                               /checkout/complete                              ✅
```

**결론**: 미구현 구간은 딱 하나 — **"예약 생성 완료 → PG prepare 호출"** 이다. 그 앞뒤는 모두 존재한다.

### B-4. 개발 계획 (요구사항 B)

#### 설계 결정: 경로 ①(체크아웃)을 폐기하고 경로 ②(BookingFlow)로 단일화

근거:
- 경로 ②만이 `TimeSlot` 을 실제로 점유한다 → 이중예약 방지가 구조적으로 성립

#### 권장안

**MVP: Daily.co** — 이유 3가지
1. **인프라 0**: PM2 단일 앱 구조(`ecosystem.config.cjs`)에 별도 WS/TURN 서버를 추가하지 않아도 된다. 현재 운영 형태와 가장 잘 맞는다
2. **접근제어가 요구사항과 정확히 일치**: 예약 ID 기준으로 룸을 만들고, 예약자·상담사에게만 만료 시간이 붙은 토큰을 발급하면 "약속 시간에 둘만 입장" 이 그대로 구현된다
3. **무료 tier 로 파일럿 가능**: 월 10,000 참가자-분 ≈ 30분 상담 약 165건(2인 기준). 초기 트래픽은 무료로 커버되고, 실측 레이턴시가 나쁘면 옵션 교체 비용이 작다

**확장/전환: Agora.io** — 파일럿에서 국내 레이턴시나 통화 품질 이슈가 확인되면 Agora 로 전환. 두 SDK 모두 "룸 생성 → 토큰 발급 → 클라이언트 입장" 구조가 같아, 아래 설계처럼 **어댑터 계층(`src/lib/videoRoom.ts`)을 두면 교체 비용이 작다.**

**Jitsi 자체호스팅**은 통화량이 커져 SaaS 과금이 부담이 되는 시점(대략 월 수천 건 이상)에 재검토.

#### 설계 (벤더 중립 어댑터)

```
src/lib/videoRoom.ts            ← 인터페이스: createRoom(reservationId) / issueToken(userId, role)
src/lib/videoRoom.daily.ts      ← Daily 구현 (MVP)
src/lib/videoRoom.agora.ts      ← Agora 구현 (확장 시)
                                   VIDEO_PROVIDER 환경변수로 스위칭
```

**스키마 추가 (Reservation)**
```prisma
  // ── 영상/음성 상담 세션 ──
  videoProvider   String?    // "daily" | "agora"
  videoRoomName   String?    // 룸 식별자
  videoRoomUrl    String?    // 입장 URL (Daily prebuilt)
  videoStartedAt  DateTime?  // 실제 입장 시각
  videoEndedAt    DateTime?
  videoDurationSec Int?      // 정산·분쟁 대응용 실제 통화 시간
```

**신규 라우트**
| 경로 | 역할 |
|---|---|
| `POST /api/reservations/[id]/room` | 룸 생성 + 토큰 발급. **가드**: `status === "CONFIRMED"` && `paymentStatus === "COMPLETED"` && (예약자 본인 \|\| 담당 상담사) && 예약 시각 ±N분 이내 |
| `POST /api/reservations/[id]/room/end` | 통화 종료 기록 (`videoEndedAt`, `videoDurationSec`) |
| `/consult/[reservationId]` (신규 페이지) | 통화 화면. 서버에서 위 가드 통과 후 룸 URL 주입 |

### C-3. 전화 상담 로직

| 방식 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **(가) PSTN 브릿지 (050 안심번호)** | 양측 실번호를 가리고 중계번호로 연결 | 실번호 비노출, 통화 품질 안정(일반 전화망), 어르신 고객 친화 | 국내는 **통신사/재판매 사업자 계약 + 심사**가 필요해 **리드타임이 길다(수 주)**. 통화당 과금. 해외 서비스(Twilio Voice)는 한국 번호 취득·발신 규제가 까다로워 실무상 부적합 |
| **(나) 앱 내 음성 통화 (WebRTC audio-only)** | C-2 에서 고른 SDK 를 오디오 전용 모드로 재사용 | **추가 비용·계약 0**, 실번호 완전 비노출, 통화 시간 자동 기록(정산·분쟁 대응), 구현 재사용 | 앱/브라우저 진입 필요, 데이터망 품질에 의존, 통화 중 앱 백그라운드 전환 처리 필요 |
| **(다) 알림톡 안내 + 상담사 직접 발신** | 예약 확정 시 양측에 시간·연락처 안내, 상담사가 직접 전화 | **구현 즉시 가능** — 알림톡 인프라 이미 존재(`src/lib/alimtalkTriggers.ts`, `AligoSendLog`, `AlimtalkTemplateSetting`) | **상담사 실번호 노출**, 통화 이력 미기록, 노쇼 분쟁 시 근거 없음 |

#### 권장안: **(나)를 본류로, (다)를 리마인더로 병행**

- 영상 상담용으로 도입한 SDK 를 `audio-only` 모드로 재사용하면 **전화 상담 구현 비용이 사실상 0** 이다. 상담사·고객 양측의 번호가 전혀 노출되지 않고, 통화 시간이 자동 기록되어 노쇼·분쟁 대응 근거가 남는다
- 동시에 **예약 확정 알림톡 + 상담 10분 전 리마인더**를 보내 입장률을 확보한다 (`notifyReservationConfirmedToCustomer` 를 여기에 연결)
- **(가) 050 브릿지는 "상담사가 앱 통화를 거부한다" 는 실사용 이슈가 실제로 확인된 뒤**에 도입한다. 계약 리드타임이 길어 선제 도입은 리스크 대비 이득이 없다

## 요구사항 D — SUPER_ADMIN 전체 조회·관리·개입 (횡단 요구사항)

> **원칙**: 상담사 쪽에 구현되는 모든 기능(독립 로그인, 예약, 영상/전화/방문 상담, 결제)은 SUPER_ADMIN 관리자 페이지에서 **전체 조회 · 관리 · 개입**이 가능해야 한다.
> 이는 A·B·C 각각의 하위 작업이 아니라 **세 요구사항 전부를 가로지르는 제약**이므로, 아래 규칙을 **모든 신규 기능의 완료 정의(Definition of Done)** 로 삼는다.

### D-1. 완료 정의 (모든 신규 기능에 적용)

상담사 기능을 하나 만들 때마다 아래 4가지가 함께 만들어져야 완료로 본다.

| 층위 | 요건 |
|---|---|
| **① 조회(Read)** | 관리자 페이지에서 **전 상담사 것을 한 화면에서** 볼 수 있어야 한다. 상담사 필터·기간 필터·검색 필수 |
| **② 관리(Write)** | 관리자가 상담사 대신 생성·수정·상태 변경을 할 수 있어야 한다 |
| **③ 개입(Override)** | 정상 플로우로는 불가능한 조작(강제 취소·강제 환불·슬롯 강제 해제·세션 강제 종료)이 가능해야 한다 |
| **④ 추적(Audit)** | 관리자가 개입한 행위는 **누가·언제·무엇을·왜** 가 기록되어야 한다 |

**API 레벨 규칙**: 모든 신규 API의 권한 검사는 반드시 아래 형태로 작성한다.

```ts
const role = session.user.role;
const isAdmin = role === "SUPER_ADMIN";
// 소유권 검사는 관리자에게는 적용하지 않는다
if (!isAdmin && !isOwner) {
  return NextResponse.json({ error: "권한이 없습니다." }, { status: 403 });
}
```

> ⚠️ 이번 검수(`13d8b6a`)에서 API 8종에 소유권 검사를 추가했다. **소유권 검사를 추가할 때 SUPER_ADMIN 우회를 함께 넣지 않으면 관리자가 차단된다.** 실제로 아래 D-3 에서 그런 사례가 1건 발견되었다.

#### 🔴 발견 1 — 관리자가 차단되는 API 1건

#### 🔴 발견 2 — 감사 로그(Audit Log) 모델이 존재하지 않는다

`prisma/schema.prisma` 전체 검색 결과 `AuditLog`·`adminLog` 계열 모델 **0건**. 즉 현재는

- 관리자가 임시 로그인으로 상담사 계정에 들어가 무엇을 했는지 **기록이 남지 않는다**
- 관리자가 예약을 강제 취소하거나 환불하면 **상담사 입장에서 원인 불명의 변경**으로 보인다

```prisma
model AdminAuditLog {
  id          String   @id @default(cuid())
  actorId     String                  // 행위자 User.id (SUPER_ADMIN)
  actor       User     @relation(fields: [actorId], references: [id])
  action      String                  // "RESERVATION_STATUS_CHANGE" | "REFUND" | "IMPERSONATE_START"
                                      // | "SLOT_FORCE_RELEASE" | "SESSION_FORCE_END" | "MEMBERSHIP_REASSIGN"
  targetType  String                  // "Reservation" | "SellerProfile" | "User" | "TimeSlot"
  targetId    String

  @@index([actorId, createdAt])

}
```

### D-5. 설계 원칙 3가지

1. **관리자 화면은 상담사 화면의 재사용으로 만든다.** `SellerReservationsClient` 와 `AdminReservationsClient` 가 이미 거의 같은 구조다. 신규 기능은 **`sellerId` 를 prop 으로 받는 공용 컴포넌트**로 만들고, 상담사 화면은 자기 `sellerId` 를 고정 주입, 관리자 화면은 상담사 셀렉터를 붙이는 방식이 유지보수 비용이 가장 낮다.
2. **개입 API 는 사유(reason) 입력을 필수로 한다.** 강제 취소·환불·슬롯 해제·세션 종료는 사유 없이는 요청을 거부하고, 그 사유를 `AdminAuditLog.reason` 에 남긴다. 상담사에게도 "관리자 조치: {사유}" 로 노출해 원인 불명 변경을 없앤다.
3. **임시 로그인은 최후 수단으로 격하한다.** 감사 추적이 어렵고 상담사 명의로 행위가 기록되므로, 전용 관리자 화면이 생긴 영역에서는 임시 로그인을 쓰지 않도록 운영 가이드를 둔다. (기능 자체는 유지 — 신규 상담사 기능의 임시 커버 수단으로 유용)

# PART 3. 추가 작업 — 메인페이지 셀러브릭스 잔재 교체 (수정 완료)

## 3-1. 증상과 원인

메인페이지 "사주메이트로 얻는 것" 섹션에 셀러브릭스 시절 문구가 그대로 노출되고 있었다.

```
사주메이트로 얻는 것 / 단골 중심 상담이 만드는 차이
68% 단골 재구매율(PICK 라이브 셀러 기준)  ·  3.2x 라이브 평균 체류(일반 대비)
50+ 활동 라이브 셀러(누적)              ·  500+ 월 라이브 방송(플랫폼 합계)
단골 PICK으로 충성 고객 / 라이브로 실시간 소통 / 정산·배송 걱정 없이
```

**원인 — 배너 FOUC와 완전히 동일한 DB 드리프트다.**

`src/lib/siteContent.ts` 는 메인페이지 콘텐츠를 `Setting` 테이블에 JSON 으로 저장하고, **DB 값이 있으면 코드 기본값보다 우선**하는 구조다(`getHomeBenefits()` L83~85).
코드 기본값(`DEFAULT_HOME_BENEFITS`)은 이미 사주메이트 문구로 바뀌어 있었으나, **운영 DB 에 셀러브릭스 시절 행이 남아 이를 덮어쓰고 있었다.** 즉 기본값만 고쳐서는 화면이 바뀌지 않는다.

운영 DB 읽기 전용 조회 결과(2026-08-12):

| Setting.key | 저장된 값 | 렌더 위치 |
|---|---|---|
| `home.benefits` | `68% 단골 재구매율` / `3.2x 라이브 평균 체류` / `50+ 활동 라이브 셀러` / `500+ 월 라이브 방송` + `단골 PICK으로 충성 고객` / `라이브로 실시간 소통` / `정산·배송 걱정 없이` | "사주메이트로 얻는 것" 섹션 |
| `home.stats` | `30억+ 누적 거래액` / `50+ 활동 라이브 셀러` / `1000+ 누적 라이브 방송` / **`98% 배송 만족도`** | "숫자로 보는 사주메이트" 다크 배너 |

> 🔎 **사용자가 지적하지 않은 잔재 1건을 추가로 발견했다.** `home.stats`(다크 배너)에도 `누적 거래액`·`활동 라이브 셀러`·**`배송 만족도`** 가 남아 있었다. 같은 원인·같은 화면이므로 함께 처리했다.

## 3-2. 수정 내용

### ① Setting 키를 v2 로 승격 — DB 드리프트 차단 (`src/lib/siteContent.ts`)

```ts
export const HOME_STATS_KEY    = "home.stats.v2";     // 구: "home.stats"
export const HOME_BENEFITS_KEY = "home.benefits.v2";  // 구: "home.benefits"

// 더 이상 읽지 않는 구 키 (정리용 참조)
export const LEGACY_HOME_STATS_KEY    = "home.stats";
export const LEGACY_HOME_BENEFITS_KEY = "home.benefits";
```

**키 교체 방식을 택한 이유**
- DB 값이 코드 기본값보다 우선하는 구조라, 기본값 수정만으로는 화면이 바뀌지 않는다
- 운영 DB 직접 수정은 DB 안전 수칙상 이 세션에서 수행하지 않는다
- 문구 블랙리스트(예: "배송" 포함 시 폐기) 방식은 관리자가 정상 입력한 값까지 걸러낼 위험이 있다
- 키 교체는 **결정적(deterministic)** 이고 오탐이 없다. 저장 경로(`saveHomeStats`/`saveHomeBenefits`)도 같은 상수를 쓰므로 관리자 수정분은 자동으로 v2 에 기록된다

> ⚠️ 구 행(`home.stats`, `home.benefits`)은 **DB 에 그대로 남아 있다.** 더 이상 읽히지 않으므로 노출은 없다. 정리하려면 관리자 > 사이트 관리 > 메인페이지 관리에서 처리하거나 DBA 가 해당 2행을 삭제하면 된다. (배너 4행과 동일한 후속 조치)

## 3-3. 수치 표기 원칙 — 성과 지표를 지어내지 않았다

요청에는 "예약 전환율, 재방문 고객 비율" 같은 성과 지표 예시가 있었으나, **실측 데이터 없이 성과 수치를 쓰지 않는 쪽을 택했다.**

- 교체 대상이던 `68% 단골 재구매율`, `3.2x 라이브 평균 체류` 자체가 근거 없는 수치였고, 이는 실제 사용자에게 노출되는 **허위 성과 표시**에 해당한다
- 대신 "플랫폼이 제공하는 것"을 나타내는 **기능형 수치**(24시간 / LIVE / PICK / 0건)로 구성했다. 설득력을 유지하면서 검증 가능한 주장만 남는다
- 이 원칙을 `siteContent.ts` 주석에 남겨 다음 수정자가 같은 실수를 반복하지 않게 했다

**실제 성과 수치를 쓰고 싶다면** — `Reservation` 집계로 계산해 주입하는 방식을 권장한다. (예: 재방문 고객 비율 = 동일 `userId` 가 같은 `sellerId` 에 2회 이상 예약한 비율). 단 요구사항 B 의 `reservations` 테이블 운영 DB 반영이 선행되어야 한다.

> ⚠️ **함께 짚어둘 점**: 신규 카피의 `0건 입금 확인 수작업` / `예약·정산 자동화` 는 **요구사항 B(예약→결제→확정)가 완료되어야 사실이 된다.** 현재 `/api/orders` POST 는 항상 400 이고 `/api/reservations` 는 결제로 이어지지 않는다. 기존 카피(`입금 확인과 일정 조율을 간편하게`)와 성공스토리(`예약·결제 자동화`)도 동일한 전제를 이미 광고하고 있다. **메인페이지가 광고하는 자동화가 실제로는 끊겨 있는 상태**이므로, 요구사항 B 를 최우선으로 처리해야 한다.
