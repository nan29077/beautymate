## 3. 운영 DB 반영 필요 사항

⚠️ **운영 RDS에는 아래 테이블/컬럼이 아직 없다.** 앱은 전역 omit + `safeQuery()` + try-catch 폴백으로 테이블 미반영 상태에서도 죽지 않게 방어돼 있으나, 기능이 실제 동작하려면 아래 DDL 반영이 필요하다.

⚠️ `prisma db push`/`migrate`는 절대 사용 금지 (전체 diff에는 뷰티메이트 레거시 테이블 DROP이 포함되어 있어 그대로 실행하면 데이터가 유실된다). 아래 **추가분 DDL만** 수동 실행할 것.

## 6. 알려진 제한사항

1. **운영 DB 테이블 미반영**: 3장의 DDL이 반영되기 전까지 예약·영상 세션·뷰티샵 회원 기능은 운영에서 "준비 중" 폴백(빈 목록/503)으로 동작한다.
2. **Daily.co 데모 모드**: `DAILY_API_KEY` 미설정 시 실제 영상 통화는 불가하고 세션 레코드·화면 플로우만 시뮬레이션된다. 운영 투입 전 키 발급 필요.
3. **Mock PG**: 실제 PG 연동 전 개발용. 운영에서 결제하려면 기존 PG(ongi/seedpay/smartropay) 경로에 예약 결제 연동 필요. 해당 콜백 3사 경로는 아직 드리프트 방어(safeQuery)가 미적용 상태(2026-08-12 검수보고서 참고).
4. **referral_commissions 이관**: 스키마는 `reservationId` NOT NULL이지만 운영 기존 데이터는 `orderId` 기반 — 컬럼 추가 시 NULL 허용으로 넣고 이관 계획 별도 수립 필요.
5. **뷰티샵 독립 로그인의 계정 체계**: 인증은 공용 `User` 계정을 그대로 사용한다(이메일 전역 unique). 동일 이메일로 뷰티샵별 별도 계정을 만들 수는 없으며, 멤버십(`shop_memberships`)으로 뷰티샵 소속만 구분한다.
